# 构建与验证清单

本文件记录 To Top 的构建环境要求、实测数据与失败修复记录。
所有数据来自本机真实执行，未执行的项目明确标注为「未验证」，不写推测值。

## 一、环境要求

| 项目 | 要求 | 本机实际 |
| --- | --- | --- |
| JDK | 17 或以上 | Microsoft OpenJDK 21.0.3 |
| Android SDK | platform 34、build-tools 34.0.0、platform-tools、cmdline-tools latest | 由 `local.properties` 的 `sdk.dir` 指定 |
| Gradle | 8.7（由 wrapper 固定） | 8.7，通过 GRADLE_USER_HOME 重定向缓存 |
| Gradle 缓存 | 不写入 C 盘用户目录 | 通过环境变量重定向到非系统盘 |
| AGP | 8.5.2 | 见 gradle/libs.versions.toml |
| Kotlin | 1.9.25 | KSP 1.9.25-1.0.20，Compose 编译器 1.5.15 |

环境变量的推荐写法（Windows PowerShell）：

    $env:JAVA_HOME        = "C:\Program Files\Java\jdk-17"
    $env:ANDROID_HOME     = "C:\Android\Sdk"
    $env:ANDROID_SDK_ROOT = "C:\Android\Sdk"
    $env:GRADLE_USER_HOME = "C:\GradleHome"

## 二、他人克隆后的配置步骤

1. 安装 JDK 17 或以上，确认 `java -version` 可用。
2. 安装 Android SDK（推荐 Android Studio 的 SDK Manager），确保存在
   `platforms;android-34` 与 `build-tools;34.0.0`。
3. 在仓库根目录复制配置模板：

       cp local.properties.example local.properties

4. 编辑 `local.properties`，把 `sdk.dir` 改为本机 SDK 路径。
   Windows 路径需要转义反斜杠，或直接使用正斜杠：

       # Windows（反斜杠需转义）
       sdk.dir=D\:\\Android\\Sdk
       # 或直接使用正斜杠
       sdk.dir=D:/Android/Sdk

   `local.properties` 已在 `.gitignore` 中排除，**绝不要提交**。
5. 可选：设置 `GRADLE_USER_HOME` 把缓存放到非系统盘，避免占满 C 盘。
6. 执行 `./gradlew :app:assembleDebug` 验证环境。

若下载依赖缓慢，`settings.gradle.kts` 已配置阿里云镜像作为兜底，
官方仓库仍然优先。

### 3.4 构建速度优化实测（2026-10-28，本机 4 核 / 16GB / JDK 21.0.3）

本轮做了一次完整诊断。`--profile` 拆解冷 daemon 下 `:app:help`（不执行任何实质任务）的 46.7 秒：

| 阶段 | 耗时 |
| --- | --- |
| Startup（daemon 冷启动） | 19.183s |
| Settings and buildSrc | 1.578s |
| Loading Projects | 2.643s |
| Configuring Projects | 13.985s（`:app` 9.484s、根 4.501s） |
| Task Execution | 0.182s |

**这 14 秒的配置阶段是一次性错觉**：它包含 AGP/KSP/Hilt/detekt 等 8 个插件的类加载与 JIT 预热。
daemon 热起来后，同样的配置阶段只剩 2-3 秒。因此「配置阶段慢」只在冷启动时成立，
真正的一等开销是 `Startup`，而配置缓存管不到它。

优化动作只做了一项：`gradle.properties` 开启 `org.gradle.configuration-cache=true`
（附 `org.gradle.configuration-cache-problems=warn` 保底）。开关前后对照，**同一 daemon 内交替跑**：

| 场景 | 关配置缓存 | 开配置缓存 |
| --- | --- | --- |
| `:app:help`（纯配置阶段） | 3s | 1-2s |
| `:app:assembleDebug`，源码无改动 | 3-7s | 2-3s |
| `:app:assembleDebug`，冷 daemon | 37s | 32s（建条目）/ 35s（复用） |
| `:app:ktlintCheck :app:detekt` | — | 31s，零违规零问题 |
| `:app:testDebugUnitTest` | — | 31s，0 失败 0 错误 0 跳过（649 项） |

如实结论：**收益只有 1-3 秒，不是数量级**。冷 daemon 下 37s 与 32-35s 的差异在噪音范围内，
因为 19 秒的 daemon 启动把能省的部分盖住了。开启它的理由是「零成本、对将来拆模块与 CI 有正向作用」，
不是「能立竿见影提速」。期望值要放对，否则会以为开了没用。

**真正的瓶颈，两处，都被人为钉死**：

| 瓶颈 | 量级 | 为什么不动 |
| --- | --- | --- |
| `ksp.incremental=false`：改任意一处源码，KSP 全量重跑 | 单次改代码构建约 26s 的主体 | KSP 增量缓存曾真实损坏（见 4.3），规范禁止回调 |
| `kotlin.compiler.execution.strategy=in-process`：没有编译守护进程预热 | 同上 | 受限环境/CI 沙箱建不起守护进程（见 4.2），规范禁止删 |
| daemon `Startup` 19s（插件类加载） | 每次 daemon 重启付一次 | 只能靠「别频繁重启 daemon」和少装插件缓解，代码层无解 |

要再快就得动上面两项，属于需要单独立项并接受风险的决定，不在常规调优范围内。

**已具备、无需再动的项**（诊断时逐条确认，避免重复优化）：

| 项 | 现状 |
| --- | --- |
| 注解处理 | 全量 KSP，源码零 `kapt`；Hilt、Room、hilt-work 均走 `ksp(...)` |
| 并行与构建缓存 | `org.gradle.parallel=true`、`org.gradle.caching=true` 已开 |
| 资源瘦身 | `res/` 仅 20 个 PNG、358KB，`mergeResources` 不是瓶颈，转 WebP 收益接近零，不做 |
| 依赖镜像 | `settings.gradle.kts` 已配阿里云兜底（官方仓库优先） |
| 模块化 | 当前单模块 `:app`，拆分是结构性工程，不属构建调优范围，需单独立项 |

**刻意不开的项**：

- `org.gradle.configureondemand=true`：单模块项目没有可省的模块，开它纯属负收益。
- `ksp.incremental`、`kotlin.compiler.execution.strategy`：两者都是踩过坑后钉死的值
  （见 4.2、4.3），不得为提速回调。


## 四、失败与修复记录

按发生顺序记录，便于复现与避免重蹈。

### 4.1 Kotlin 1.9.24 编译器内部错误

现象：`compileDebugKotlin` 抛出

    org.jetbrains.kotlin.codegen.CompilationException:
    Back-end (JVM) Internal error: Couldn't transform method node ...
    Caused by: java.lang.NullPointerException
        at ...FixStackAnalyzer$InternalAnalyzer.executeAfterInlineCallMarker

触发代码位于 `LlmClient` 的「挂起函数 + channelFlow + 内联 lambda + 循环跳出」组合。

处理：Kotlin 升到 1.9.25，KSP 同步 1.9.25-1.0.20，Compose 编译器 1.5.15。
结论：1.9.24 后端缺陷，1.9.25 已修复；1.9.x 补丁线内 API 一致。**禁止回退。**

### 4.2 Kotlin 编译守护进程无法连接

现象：`Could not connect to Kotlin compile daemon`，构建自动回退到进程内编译并成功。

处理：在 `gradle.properties` 固定 `kotlin.compiler.execution.strategy=in-process`，
使受限环境与 CI 沙箱也能稳定构建。代价是失去增量编译守护进程，可接受。

### 4.3 KSP 缓存损坏

现象：`java.nio.file.NoSuchFileException: app/build/kspCaches/debug/backups/java`
或 `generated/ksp/debug/java/byRounds/1/..._GeneratedInjector.java`。

原因：**多个进程并行构建同一个工程**，互相删除对方的中间产物。

处理：清理 `app/build` 后重建。**收口与日常验证必须串行执行**，
并行开发时各自使用独立副本目录。

### 4.4 ktlint 误报 Composable 命名

现象：`ToTopTheme`、`SolveScreen` 等全部被 `standard:function-naming` 报错。

原因：Compose 官方约定 @Composable 函数用 PascalCase，与 Kotlin 普通函数的小驼峰规则不同。

处理：在 `.editorconfig` 加入

    ktlint_function_naming_ignore_when_annotated_with = Composable, Preview

这是 ktlint 官方为该场景提供的属性，不是关闭规则。

### 4.5 detekt 配置项归属错误

现象：`Property 'complexity>ThrowsCount' is misspelled or does not exist`、
`Property 'exceptions>ThrowsCount'`、`Property 'test-patterns'` 等。

原因：detekt 1.23.6 中 `ThrowsCount` 属于 `style` 规则集；
`LoopWithTooManyJumpStatements` 同样属于 `style`；
`test-patterns` 与 `style>OutdatedDocumentation` 在该版本不存在。

处理：逐条按报错把规则移到正确规则集，删除不存在的属性。
detekt 的报错信息会直接给出正确路径，按提示改即可。

### 4.6 Hilt + WorkManager 初始化冲突（已修复）

现象：应用启动后运行后台任务时崩溃，提示 Worker 无法实例化。

原因：`App` 实现了 `Configuration.Provider` 并提供 `HiltWorkerFactory`，
但没有关闭 androidx.startup 的 WorkManager 自动初始化，
导致 WorkManager 先用默认配置建实例，Hilt 注入不生效。

处理：在 `AndroidManifest.xml` 中用 `tools:node="remove"` 移除
`androidx.work.WorkManagerInitializer` 的自动初始化。

### 4.7 依赖缺口

成员报告过的缺口已补齐，均在 `gradle/libs.versions.toml` 中：

- `androidx.hilt:hilt-work` 与 `androidx.hilt:hilt-compiler`（`@HiltWorker` 必需）
- `androidx.room:room-testing` 的 `androidTestImplementation`（MigrationTestHelper 必需）
- `androidx.test:core` 独立版本键（不能复用 ext.junit 的版本）

### 4.8 CI 全红的三处真实成因（2026-10-23 定位并修复）

**成因一：gradlew 在 Linux runner 上没有可执行位（exit code 126）。**

工作流日志给出的唯一失败注解就是 `Process completed with exit code 126`，
126 在 shell 里的含义是「命令不可执行」，而不是脚本内部报错。
根因是开发机为 Windows，git 的 `core.fileMode=false` 不记录可执行位，
`gradlew` 以 `100644` 入库；Ubuntu runner 检出后直接执行 `./gradlew` 便是 Permission denied。

修复：`git update-index --chmod=+x gradlew` 把索引里的模式改为 `100755`，
并在 `ci.yml` 的两个作业与 `release.yml` 中统一加一步 `chmod +x gradlew`。
两道保险并存：前者修正仓库事实，后者保证任何检出方式（含归档下载、缓存恢复）都能跑。

**成因二：`lintDebug` 有 2 个 error，而它从未进入本地门禁。**

| 位置 | 规则 | 真实问题 |
| --- | --- | --- |
| `ReviewReminderWorker.kt` | MissingPermission | 发通知处只有外层 `canNotify()` 判定，Lint 只看本函数体，判成漏检 |
| `ExportSink.kt` | NewApi | `MediaStore.Downloads.getContentUri` 是 API 29 API，调用点有版本判定但私有方法未标注 |

两处都不是误报，而是「写法上确实没有把安全性交待在调用点上」。
修复分别是：在 `notify()` 内补齐同语义的权限判定并提前返回；
给 `publishToDownloads()` 标注 `@RequiresApi(Build.VERSION_CODES.Q)`（调用方已有 SDK_INT 判定）。
没有往 `lint-baseline.xml` 里塞抑制——那份基线约定只登记确认过的误报。

**成因三：签名 keystore 路径解析基准错位。**

旧代码在 `android {}` 块内写 `storeFile = file(releaseStoreFile)`。
Gradle 的 `file()` 以**模块目录** `app/` 为基准，而 CI 把 `release.jks` 落在**仓库根目录**，
于是 `RELEASE_STORE_FILE=release.jks` 被解析成不存在的 `app/release.jks`。
因为代码只设路径、不校验存在性，`assembleRelease` 不报错，只是**静默产出 unsigned 包**，
要等到后面的「校验产物与体积门禁」步骤才以完全不相干的报错暴露出来。

修复：在顶层作用域预先展开成「模块目录 → 仓库根目录」两级候选，取第一个真实存在的；
候选全不存在时立即抛 `GradleException` 并列出尝试过的全部路径。
保留模块目录语义是为了不破坏 `local.properties.example` 里的 `../keystore/release.jks` 写法，
新增根目录语义是为了匹配 CI 的裸文件名写法，两者都实测通过。

### 4.9 配置缓存与 `--profile` 不能同时用

现象：开着配置缓存跑 `./gradlew :app:help --profile`，任务本身 BUILD SUCCESSFUL，
但构建末尾报

    Could not write to file 'reports\profile\profile-1970-01-01-08-00-00.html'
    > Unable to create directory 'reports\profile'

原因：`--profile` 的报告路径是**相对路径**，配置缓存恢复的上下文中没有可用的
项目基准目录，于是顺着相对路径落到了进程工作目录，时间戳也退化成 1970。
这是 Gradle 8.7 的既有行为，与本项目脚本无关。

处理：做性能分析时临时关掉配置缓存，两者不共存：

    ./gradlew :app:help --profile --no-configuration-cache

日常构建不需要 `--profile`，所以不影响使用；只影响「想量一下耗时」的场景。


## 六、注意事项

1. **构建必须串行**：多个 Gradle 进程同时构建同一工程会破坏 KSP 缓存（见 4.3）。
2. **不要回退 Kotlin**：1.9.24 无法编译本项目（见 4.1）。
3. **不要删除 in-process 编译配置**：删除后在受限环境会反复失败（见 4.2）。
4. **local.properties 永不提交**：签名材料同理，只走 CI Secrets。
5. **release 体积门禁**：CI 在 `release.yml` 中校验不超过 30MB，超限直接失败。
6. **真机性能另测**：本文件只覆盖构建与静态检查，低端机性能见
   [docs/低端机测试清单.md](低端机测试清单.md)。
7. **改了 `gradle.properties` / `build.gradle.kts` / 版本目录后，下一次构建会重新建配置缓存**
   （慢一次，之后恢复）。这不是回归，不要急着去关配置缓存。
