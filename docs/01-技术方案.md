# ToTop 技术方案

> 面向安卓 / iOS / 鸿蒙三端的「考试失分分析」工具。核心链路：导入试卷与答题卡 → 多模态 AI 归因 → 趋势跟踪 → 点数计费。

## 1. 需求拆解

| 编号 | 需求 | 落地方式 |
| --- | --- | --- |
| R1 | 拍照 / 导入 PDF、Word 等文件导入**题目** | `uni.chooseImage` + `uni.chooseFile`；后端对象存储 + 文档解析（PDF/Word 转文本与图片） |
| R2 | 拍照 / 导入 PDF、图片导入**答题卡** | 同上；额外记录「是否已批改」标记，决定 AI 是判分还是归因 |
| R3 | 多模态 AI 分析失分知识点、所属模块、提升指南 | 阿里云百炼 Qwen-VL（`qwen-vl-max` / `qwen3-vl`），强结构化 JSON 输出 |
| R4 | 适配 Android / iOS / HarmonyOS | uni-app（Vue3 + TS）一套代码，三端分别打包 |
| R5 | 三个 Tab：趋势 / 导入 / 账号 | `pages.json` 的 tabBar；趋势页用 Canvas 折线图展示各科与总分得分率 |
| R6 | 账号体系：手机号注册、可绑定密码、验证码或密码登录 | JWT（access + refresh），短信验证码，开发模式固定 123456 |
| R7 | 计费：注册送 1 点数，每次分析扣 1 点数 | 点数账本 `credit_ledger` + 原子扣减 |
| R8 | 变现：看 10 次激励视频 = 1 点数；充值 1 元 = 1 点数（iOS 1.5 元） | 广告回调幂等累计；支付渠道见 [04-支付与变现](04-支付与变现.md) |

## 2. 总体架构

```
┌──────────────────────── 客户端（uni-app / Vue3 / TS）────────────────────────┐
│  Tab1 趋势             Tab2 导入                 Tab3 账号                    │
│  Canvas 折线图          拍照/相册/文件选择        验证码/密码登录              │
│  考试列表               上传+登记题目与答题卡      点数余额 / 看广告 / 充值      │
│  概览卡                 触发 AI 分析 + 进度         点数明细 / 设置             │
│                          ↓ 结果摘要 → 分析详情页                              │
└───────────────────────────────────┬──────────────────────────────────────────┘
                                    │ HTTPS + JWT
┌───────────────────────────────────▼──────────────────────────────────────────┐
│                      API 网关（Nginx + FastAPI /api/v1）                      │
│  auth 认证 │ users │ credits 点数 │ orders 订单 │ exams 考试                   │
│  uploads 上传 │ analyses 分析 │ trends 趋势 │ meta 字典                        │
└───────┬───────────────┬────────────────┬─────────────────┬───────────────────┘
        │               │                │                 │
   PostgreSQL        Redis           对象存储            外部服务
   用户/考试/分析    验证码/限流/      OSS/COS/MinIO      Qwen-VL（百炼）
   点数账本/订单     任务进度缓存      原图与解析结果      短信服务 / 广告平台 / 支付
```

### 为什么后端要独立（而不是纯前端直连模型）

1. **API Key 绝不能进客户端**：模型 key 一旦打进包体即等于泄露。
2. **计费必须在服务端**：点数的扣减、广告回调校验、支付回调验签都必须在可信环境。
3. **重任务要异步化**：一份试卷 + 多张答题卡的视觉推理耗时 20~60 秒，客户端只轮询任务状态。
4. **数据可复用**：历史成绩、趋势、错题沉淀在服务端，换机不丢。

## 3. 技术选型与理由

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 客户端 | uni-app（Vue3 + TS + Vite） | 唯一同时官方支持 Android / iOS / **HarmonyOS NEXT** 的主流跨端框架（`@dcloudio/uni-app-harmony`）；国内广告、支付、统计插件生态最全；团队只需 Vue 技能 |
| 图表 | 自研 Canvas 折线图组件 | 不引入 ECharts 等重依赖，三端（含鸿蒙）渲染行为一致，尺寸与交互完全可控 |
| 后端 | Python 3.13 + FastAPI | PDF/Word 解析（PyMuPDF / python-docx）、图像预处理（Pillow / OpenCV）、AI SDK 生态最好；异步 IO 适合以"等待模型"为主的负载 |
| 数据库 | PostgreSQL + SQLAlchemy 2.0 (async) | JSONB 存 AI 结构化结果；事务保证点数扣减的原子性 |
| 缓存 | Redis | 短信验证码、接口限流、任务进度；不可用时自动降级为内存计数 |
| 存储 | 对象存储（OSS / COS / MinIO） | 试卷与答题卡图片体积大，不落应用服务器磁盘 |
| 模型 | 阿里云百炼 Qwen-VL | 中文试卷与手写体识别强、发票合规、国内直连延迟低；抽象成 Provider 接口便于切换 |
| 密钥/配置 | `.env` + pydantic-settings | 不同环境（本地 / 测试 / 生产）只换配置不改代码 |

## 4. 前端设计

### 4.1 页面结构

```
pages/
├── trend/index.vue      Tab 1  趋势
├── import/index.vue     Tab 2  导入
├── account/index.vue    Tab 3  账号
└── analysis/index.vue   详情页（navigateTo，非 Tab）
```

> 说明：主导航严格是 3 个 Tab。分析结果详情单独成页，因为内容量大（逐题证据 + 提升指南 + 周计划），塞进 Tab 会让导入流程页面过长且丢失上下文。

### 4.2 趋势页（Tab 1）

- **概览卡**：最近一次总分得分率 + 环比（百分点）+ 最强/最弱学科 + 考试次数
- **学科筛选 chips**：多选，控制折线图中显示哪些学科
- **折线图**：纵轴为**得分率百分比**（非原始分），因为不同学科满分不同，原始分不可比
  - 总分线加粗（3px）作为基准，学科线 2px
  - 纵轴下限按数据自适应（`min-0.08` 向下取整），避免曲线挤成一条直线
  - 点击/滑动出现十字准线与浮层，显示该次考试各科得分率
  - 点击图例可临时隐藏某条线，「总分」不可隐藏
- **历次考试列表**：名称、日期、科目数、分析状态徽标、得分率与环比

### 4.3 导入页（Tab 2）

三步式引导，状态在页面上顺序呈现：

1. **选择/新建考试**（当前考试的上下文，所有导入都挂在它下面）
2. **导入题目**：拍照 / 相册 / PDF·Word；支持多张
3. **导入答题卡**：先选「老师已批改 / 未批改」，再拍照 / 相册 / PDF·图片
4. **开始分析**：显示消耗点数与余额 → 二次确认弹窗 → 进度条（识别→比对→归因→生成计划）→ 结果摘要 → 进入详情页

关键交互细节：

- 余额不足时不静默失败，直接弹出「去获取点数」并跳转账号页
- 上传中显示 loading 遮罩，成功后本地列表即时更新（乐观更新）
- 演示模式（`USE_MOCK`）下不请求网络，用结构化假数据完整走通流程

### 4.4 账号页（Tab 3）

- **未登录**：品牌区 + 「验证码登录 / 密码登录」切换 + 协议勾选
  - 验证码登录时，未注册手机号自动注册并赠送 1 点数（`loginBySms` 失败且错误码为"用户不存在"时自动 `register`）
  - 开发/演示模式会把验证码回显并提示
- **已登录**：用户卡、点数余额、「看视频得点数」进度条（`3/10` 形式）、充值套餐、点数明细、设置项
  - 套餐按平台切换：iOS 显示 IAP 套餐（¥1.50/点），Android/鸿蒙显示微信/支付宝套餐（¥1.00/点）

### 4.5 状态与数据流

- Pinia `user` store 持有登录态与点数，`token` 落本地 storage，冷启动 `bootstrap()` 静默恢复
- 所有接口集中在 `src/api/index.ts`，每个接口都带 `fallback`：真实请求失败时自动降级为演示数据，保证界面永不空白
- 401 统一处理：清 token → toast → 跳账号页

## 5. 后端设计

### 5.1 模块划分

```
app/
├── api/v1/endpoints/   auth users credits orders exams uploads analyses trends meta
├── core/               config security(JWT/密码) errors rate_limit
├── db/                 async engine + session
├── models/             SQLAlchemy 2.0 ORM
├── schemas/            Pydantic v2 出入参
├── providers/ai/       base / qwen（真实） / mock（演示）
├── providers/storage/  local / s3
├── services/           analysis(编排) credits(账本) sms(验证码)
└── tasks/              asyncio 后台任务 + 状态表（不引入 Celery）
```

### 5.2 分析任务编排（`services/analysis.py`）

```
POST /analyses
  ├─ 1. 校验考试归属、答题卡存在、点数是否足够
  ├─ 2. 原子扣费：UPDATE users SET credits = credits - 1 WHERE id = ? AND credits >= 1
  │      影响行数为 0 → 返回 402xx「点数不足」，不产生任何副作用
  ├─ 3. 创建 Analysis(status=pending) + 写 CreditLedger(delta=-1, 幂等键)
  ├─ 4. 派发后台任务：取题目文本 + 答题卡图片 → 组装 Prompt → 调 Provider
  ├─ 5. 模型返回 JSON → 校验 schema → 落库 result → 回写各科得分率 → status=succeeded
  └─ 失败：status=failed + error，并写一条 delta=+1 的退还流水（refund）
```

前端通过 `GET /analyses/{id}` 轮询 `status`，直到 `succeeded` / `failed`。

### 5.3 计费与幂等

| 场景 | 幂等键 | 说明 |
| --- | --- | --- |
| 分析扣费 | `analysis:{analysis_id}` | 重试同一分析不重复扣费 |
| 广告奖励 | `ad:{event_id}` | 平台回调可能重发，同一 `event_id` 只计一次进度 |
| 注册赠送 | `register:{user_id}` | 一人一次 |
| 充值到账 | `order:{order_no}` | 支付回调可能重发 |

## 6. 数据模型（核心表）

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `users` | phone(唯一)、password_hash、credits、invite_code | 点数余额冗余在用户表，账本表存明细 |
| `credit_ledger` | delta、reason、balance_after、idempotency_key(唯一) | 任何点数变动都必须写账本 |
| `ad_events` | platform、event_id(唯一)、credited | 广告进度累计与去重 |
| `orders` / `plans` | order_no、channel、status、third_party_txn_id | 支付与套餐 |
| `exams` | user_id、name、exam_date、grade、total_full_score | 一次考试 |
| `papers` | exam_id、subject_code、source_type、object_keys、ocr_text | 题目/试卷 |
| `answer_sheets` | exam_id、is_graded、object_keys、score、full_score | 答题卡，`is_graded` 决定 AI 策略 |
| `import_tasks` | kind、status、progress、message | 上传/OCR 任务进度 |
| `analyses` | status、result(JSON)、credits_cost、model_name、tokens | AI 分析结果 |
| `knowledge_modules` | subject_code、name、parent_id | 学科→模块→章节三级字典，用于把失分点归类 |

## 8. 关键风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 手写答题卡识别不准 | 归因结果不可信 | 默认走「已批改答题卡」路线；拍照时给出清晰拍摄引导；低置信度字段在结果页标注"待确认" |
| 模型输出不是合法 JSON | 解析失败、任务失败 | `response_format=json_object` + 后端 schema 校验 + 失败自动重试一次（提高 temperature 之外的稳定性） |
| 单次分析成本高于 1 元收入 | 亏本 | 上传前压缩图片（长边 1600px）、限制单次答题卡页数、缓存题目 OCR 结果、必要时按科目分批调用小模型 |
| K12 学科培训监管 | 上架受阻 | 定位为**学习工具**而非培训服务：不提供课程、不承诺提分、不做排名对比；详见 04 文档 |
| 未成年人个人信息 | 合规风险 | 隐私政策明示、最小化收集、支持删除；必要时引入家长同意流程 |
| 点数被刷 | 直接损失 | 注册赠送做设备+手机号双限、广告回调验签、分析接口限流 |
