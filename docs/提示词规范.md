# 提示词规范

本文定义四个阶段提示词的组织方式、约束、版本管理与评审流程。
提示词正文在 `app/src/main/assets/prompts/`，属于数据而非代码，改文案不需要改 Kotlin。

## 一、为什么必须分阶段

让模型在同一次调用里既解题又找错，会被学生的错误思路带偏：模型看到学生的错误步骤后，
容易顺着错误路径给出「看起来合理」的解答，最终既没解对题，也没找准错因。

因此强制拆成四次调用：

| 阶段 | 文件名 | 看到什么 | 产出 |
| --- | --- | --- | --- |
| A 识题 | `stage_a_identify.md` | 图片或 OCR 文本 | 结构化题目 |
| B 独立求解 | `stage_b_solve.md` | 只有题目 | 标准解答链 |
| C 错因定位 | `stage_c_locate_error.md` | 题目、标准解答、学生过程 | 首个错误步骤与错因 |
| D 知识点抽取 | `stage_d_kpoints.md` | 题目、解法要点、候选知识点 | 受控 ID 的知识点 |

其中阶段 B 的输入结构体中**没有**学生过程字段，这是代码层面的物理隔离，
不依赖提示词里的「请不要参考学生做法」这类软约束。

## 二、文件结构约定

每个提示词文件必须包含以下六节，顺序固定：

1. 角色：一句话说明模型扮演谁，以及唯一职责
2. 输入：逐字段说明输入内容，明确哪些信息不会出现
3. 必须输出：字段表格，含类型与取值要求
4. 禁止事项：编号列举，覆盖该阶段最容易出错的偏航行为
5. JSON Schema：可直接粘贴的 schema，`additionalProperties` 为 false
6. 正确示例：一组完整输入与对应输出

补充要求：

- 全文中文，禁止 emoji
- 不使用 Markdown 之外的装饰性符号
- Schema 中的字段名必须与客户端 DTO 完全一致，大小写一致
- 示例必须是真实可解的题目，不能编造无解或矛盾的题

## 三、各阶段硬约束

### 3.1 阶段 A 识题

禁止：

- 给出任何解题步骤、中间结论或最终答案
- 补写图片中不存在的条件
- 在 JSON 前后添加说明文字
- 猜测学段年级，无法判断时填「未知」

关键点：识别错字允许修正，但必须在 `warnings` 中记录修正内容，保证可追溯。

### 3.2 阶段 B 独立求解

禁止：

- 提及学生、学生的做法、学生的错误
- 给多种答案或讨论「另一种可能」
- 跳过关键推理直接给结论

关键点：步骤链至少 2 步，每步必须同时有「做什么」与「为什么」，
`why` 要指向所用定义、定理或公式，不能写「显然」「易得」。

### 3.3 阶段 C 错因定位

禁止：

- 新增错因类型，只能取固定七类
- 给出多个不同的最终答案
- 在学生未提供过程时编造学生步骤

关键点：必须定位**第一个**错误步骤，而不是列举所有错误。
后续错误往往由第一个错误连带产生，全部列出会让学生抓不住重点。
学生过程为空时 `firstError` 必须为 null，并在摘要卡中说明原因。

**错因口径：完全不会 != 步骤缺失。**
学生明确说「不会」「没思路」时，取 `方法选择不当`（他没进入这道题的解法）；
`步骤缺失` 只用于「有过程但漏了关键一步」。这个区分直接影响错因统计：
把完全不会判成步骤缺失，统计会显示「步骤缺失」偏多，
而真实短板其实是「不知道从哪里切入」，复习方向会被带偏。
本条自 1.1.1 起生效。

**多小问要标 `subQuestion`（自 1.3.0 起）。**
`firstError.stepIdx` 是**学生步骤**的序号，标准步骤是另一套编号，两者只在同一问内步序大致对应时
才碰巧一致；学生跳步时按序号推位置会把提示指到上一问。所以阶段 C 必须同时给出
`subQuestion`（1 起，与标准步骤里 `(1)` `(2)` 的编号一致），整题不分问或判断不出时取 `null`。
禁止拿 `stepIdx` 的值去填 `subQuestion`。

### 3.4 阶段 D 知识点抽取

禁止：

- 自造知识点 ID
- 输出候选清单之外的知识点
- 把「未分类」当作知识点使用

关键点：`id` 必须严格匹配 `^KP_<学科>_[0-9]{4}$`，且必须出现在候选清单中；
`name` 必须与清单中该编号的名称完全一致；候选确实无法覆盖时
把 `unmatched` 置为 true，由客户端归入未分类并提示补充知识点树。

## 四、输出校验与重试

    AI 原始文本
      -> 严格反序列化（忽略未知字段、显式 null 视为缺省）
      -> 结构性校验（关键结构是否齐全）
      -> 语义清洗（受控 ID、错因枚举归一）
      -> 通过：落库；不通过：以更严格提示词重试 1 次
      -> 仍不通过：提示用户，绝不写入数据库

重试不是把原提示词再发一遍，而是在重试请求中追加一段更严格的要求，
例如「只输出 JSON，不要任何解释文字」「字段必须齐全」。

告警处理原则：语义清洗产生的告警（例如 AI 返回了非受控 ID）写入日志并计数，
绝不静默丢弃，否则统计会悄悄失真。

## 五、版本管理

版本号在 `app/src/main/assets/prompts/prompt_version.json`，参与缓存键计算。

| 变更类型 | 版本升级 | 示例 |
| --- | --- | --- |
| 措辞调整、示例修正 | PATCH | 把「易得」改为要求写出依据 |
| 输出字段增删改 | MINOR | 阶段 A 增加 stemLatex 字段 |
| 阶段边界变化、阶段拆分或合并 | MAJOR | 把阶段 C 拆成错因定位与思维对比两次调用 |

强制规则：

1. 只要提示词文件内容有任何改动，就必须升级版本号，否则旧缓存会被错误复用
2. 升级版本号后，旧缓存条目自动失效，不需要手动清理
3. 不允许混用不同版本的解析结果
4. 版本号变更必须与提示词文件在同一次提交中完成

## 六、评测流程

改提示词是高危操作，容易「改好一题坏掉十题」。因此建立固定评测集：

1. 在 `docs/eval/` 下准备 30 至 50 道真实错题，覆盖各学段、各错因类型、手写与印刷体
2. 每次修改提示词后，对全量评测集跑一遍四个阶段
3. 记录阶段成功率：识题字段完整率、解答正确率、错因命中率、知识点映射命中率
4. 只有各项指标均不下降才允许合并
5. 评测结果文件命名 `eval-YYYYMMDD-简述.md`，随 PR 一并提交

评测集本身要注意：不得包含真实学生的个人信息，题目图片需脱敏。

## 七、成本约束

提示词直接影响 token 消耗，编写时必须注意：

- 不在提示词中列举全部知识点，只传检索到的候选清单（建议不超过 10 条）
- 不复述整段学生过程，只传必要的步骤文本
- 明确要求输出简洁，避免模型长篇大论
- 单阶段输出上限按需设定（阶段 A 约 800，阶段 B 与 C 约 2048，阶段 D 约 512）
- 提示词自身的固定开销也要控制，避免每次调用都携带大段无关说明

## 八、评审清单

提交提示词改动时，评审者逐项检查：

- [ ] 六节结构完整，顺序正确
- [ ] Schema 与客户端 DTO 字段名完全一致
- [ ] 禁止事项覆盖该阶段已知的偏航行为
- [ ] 正确示例真实可解，输出与 Schema 完全匹配
- [ ] 版本号已同步升级，并在提交信息中说明升级类型
- [ ] 已跑评测集且指标不下降
- [ ] 没有引入 emoji
- [ ] 没有把学生过程传入阶段 B

## 九、常见失误

| 失误 | 后果 | 正确做法 |
| --- | --- | --- |
| 在阶段 B 提示词里提到「学生」 | 模型开始猜测学生做法，解答被带偏 | 阶段 B 输入结构与提示词都不得出现学生信息 |
| 改错因类型以「更贴合本题」 | 统计口径崩坏，七类失去可比性 | 错因类型固定七类，只能调整 explain 措辞 |
| 让模型自由命名知识点 | 自造 ID 导致统计碎片化 | 只允许映射候选清单中的受控 ID |
| 改了提示词忘了升版本 | 旧缓存被复用，用户看到旧结果 | 任何文本改动都升版本号 |
| 让模型一次输出全部阶段结果 | 阶段混淆，错因定位失准 | 严格四阶段拆分，各自独立调用 |
