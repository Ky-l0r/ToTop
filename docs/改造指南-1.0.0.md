## 一、这一版到底在做什么

### 1.1 两件事

| 序号 | 事项 | 性质 | 判断标准 |
| --- | --- | --- | --- |
| 一 | 底座从 Android 原生换成 UniApp，同时出 Android 与 iOS | 重写 | 同一份代码能出两个包，页面逻辑只写一遍 |
| 二 | 把十年前的老机假设从设计里拆掉 | 减法 | 动画、图表、列表、图谱不再有"因为机器慢所以不做"的禁令 |

### 1.2 已拍板的三条决策

| 决策 | 结论 | 影响的章节 |
| --- | --- | --- |
| 目标端 | Android + iOS；H5 只用于调试，不作为交付物；本期不做小程序 | 3.1 / 3.4 / 8.3 |
| 迁移方式 | 渐进双轨：0.8.0 原生版冻结为参照实现，只修致命缺陷；UniApp 按页搬迁 | 3.2 / 3.6 |
| 性能放开尺度 | 放开表现层，保留兜底：动画、图表、列表条数不再限制；图片压缩与公式渲染保留分级降档 | 四章 |

### 1.3 1.0 的性质：功能列表必须比 0.8.0 短

0.8.0 有十一个入口，其中四个是半成品（复习打卡、卡点笔记、掌握度图表、资料库存解析）。
1.0 砍掉它们，把省下来的力气放在**拍题页的呈现质量**上。
如果 1.0 做完之后功能比 0.8.0 还多，说明这一版跑偏了。

### 2.2 现有"旧安卓性能限制"清单

这些约束散落在 `docs/架构.md`、`docs/工程规范与构建说明.md` 与 `AGENTS.md` 里，
当年成立的理由是"目标机型为 4GB 内存的中低端老机"。1.0 逐条处置：

| 编号 | 旧限制 | 出处 | 当年为什么 | 1.0 处置 |
| --- | --- | --- | --- | --- |
| L1 | 图片长边 ≤ 1280、JPEG 0.78 | 架构 三章 | 省流量、省内存 | 默认 1600、0.85；低端机与大图自动降到 1280 |
| L2 | 只打 arm64-v8a | 工程规范 七章 | 包体 30MB 门禁 | 双端天然分架构，门禁改为按端计（Android 80MB 内） |
| L3 | 只做位移+淡入+极轻缩放，禁毛玻璃/共享元素/循环动画 | AGENTS 5.6 | 老机掉帧 | 放开到"有节制的动效"：允许共享元素、允许淡入叠化、允许一次性循环（如思考指示），仍禁大面积毛玻璃与视差 |
| L4 | 图表降采样 ≤ 60 点、canvas、关动画 | 架构 十章 | 老机渲染慢 | 保留降采样但抬到 120 点；允许入场动画；图谱允许交互式缩放 |
| L5 | 图谱预计算坐标、单屏 ≤ 80 节点 | 架构 七章 | 运行时力导向算不动 | 保留预计算（不是性能问题，是稳定性问题），节点上限抬到 150 |
| L6 | 列表分页 200 条、缩略图懒加载 | 架构 十章 | 内存 | 分页保留（改为 50 条一页按需拉），缩略图保留 |
| L7 | 禁用动态取色 | 工程规范 六章 | 零额外计算 | 保留（理由改为品牌一致性，不再是性能） |
| L8 | 因 minSdk 24 路由不用对象序列化 | 工程规范 五章 | 兼容性 | 放开，路由可传结构化参数 |
| L9 | 公式渲染 WebView 实例复用 | 架构 十章 | 老机 WebView 创建慢 | 改为"每屏一个宿主 + 渲染结果缓存"；iOS 端无复用压力，按端配置 |
| L10 | 启动动画固定 620ms | 导航宿主 | 掩盖冷启动 | 改为跟随真实就绪时间，最快 320ms |

### 2.3 规模参照

0.8.0 有 379 个 Kotlin 文件，界面层约 2 万行，其中复习资料的 PDF 自绘就占 1169 行。
这意味着：**不可能"顺手"完成这次迁移**，必须分批、必须允许中间态不可用。

## 三、底座一：UniApp 多端迁移

### 3.1 选型与工程形态

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | uni-app + Vue 3 + TypeScript | 一套代码出双端；生态里 WebView 与本地库能力最全 |
| 构建 | Vite，条件编译区分 android / ios | 平台差异集中在一处，不散落进页面 |
| 状态 | Pinia，按页分 store | 对齐现在 ViewModel + StateFlow 的粒度 |
| 存储 | 端上 SQLite，H5 用 IndexedDB（仅调试） | 数据量（题目、错题、知识点树 740 节点）不适合键值存储 |
| 样式 | 统一 design token，禁止页面内写死颜色 | 沿用现有 `ui/theme/Tokens.kt` 的语义色命名 |

### 3.2 三棵树的职责

```
仓库根
  legacy/android/        0.8.0 原生工程，冻结。只修致命缺陷，不做功能
  apps/mobile/           UniApp 工程，1.0 的唯一交付物
  packages/core/         纯 TypeScript 的领域层：掌握度、间隔重复、错因分类、题型判定
docs/                    规范与实施文档
```

关键约束：`packages/core` 不许 import 任何 uni 或平台 API，保证可在 Node 里单测。
这条对齐现在"领域层不依赖 Android SDK"的规矩，不可放宽。

### 3.4 能力映射：六项要重做，两项是红利

| 能力 | 0.8.0 实现 | 1.0 方案 | 风险 |
| --- | --- | --- | --- |
| 相机与框选 | CameraX + 自绘裁剪 | uni 相机组件 + 自绘裁剪层 | 中 |
| 离线 OCR | ML Kit bundled | 取消离线 OCR，统一走视觉模型 | **高** |
| 公式渲染 | assets 内置 KaTeX + 复用 WebView | 直接用 WebView 渲染 KaTeX | 低（红利） |
| 本地数据库 | Room | SQLite（端上）/ IndexedDB（H5 调试） | 中 |
| 密钥加密 | Android Keystore | 端上安全存储插件；H5 只做会话内存储 | **高** |
| PDF 导出 | 1169 行自绘 PDF | HTML 排版 + 系统打印/分享 | 中 |
| 后台任务 | WorkManager 日汇总 | 取消定时任务，改为进页面时增量补偿 | 低 |
| 语音输入 | 系统/第三方 ASR 桥接 | 端上 ASR 插件，H5 降级为文字 | 中 |

#### 3.4.1 离线 OCR 取消，是这次迁移最大的一次取舍

0.8.0 的路由逻辑是"印刷体且置信度 ≥ 0.80 且无图形 → 纯文本模型，否则视觉模型"。
UniApp 双端没有等价的离线 OCR，可选三条路：

| 方案 | 代价 | 后果 |
| --- | --- | --- |
| 甲：全部走视觉模型 | 单题成本从 1.5K 涨到 3K-8K token | 省钱的路由没了，但链路最短、最稳 |
| 乙：引入端上 OCR 原生插件 | 双端各写一次桥接，工期 +8 到 10 人日 | 保留成本优势，但插件质量不可控 |
| 丙：接第三方云 OCR | 图片会发往第二个地址 | **违反"图片只发往用户自己配置的模型端点"，直接否决** |

建议先走甲，把乙留作 1.1 的优化项。代价要写进 `docs/偏离记录.md`：
**"1.0 不再有本地识别，每次拍题都会调用一次视觉模型。"**
这句话同时要出现在设置页的用量说明里，让学生自己看得见成本变化。

#### 3.4.2 本地数据库

表结构基本照搬，六处要改（列名一律 camelCase，与 0.8.0 对齐，导入时是逐列拷贝）：

| 表 | 改动 | 原因 |
| --- | --- | --- |
| mistake_record | 保留 `status` 列只作导入兼容，界面不再读它；新写入不再产生状态值 | 见 5.6 |
| 新增 solution_revision | 改写前的完整解答（步骤 + 答案）存一版，`mistakeId` 作主键，一道题只留一版 | S-24、S-54 |
| study_note | 保留表、不迁入口 | 卡点笔记下线，但已写的内容不能丢 |
| exam_score | 新增 `importedAt`（录入时间），用于"该科最近一次导入"排序 | 见 5.11 T-2 |
| 新增 material | **一张表装下整个资料库**：标准答案与旧方法卡同表，用 `source` 区分（`standard_answer` / `legacy_card`） | 见 5.9 |
| question | 新增 `questionType`（学科×题型）与 `choiceType`（单/多选判定） | S-28、S-49 |

两张新表的具体取舍：

- `solution_revision` 只留一版，不做历史栈：学生会回退，但几乎不会回退两次。
- 资料库没有按原计划拆成 `material` + `material_source` 两张表。来源只是同一条资料的属性，
  拆表会让"列出全部资料"变成一次 join，而这里根本不需要 join。

#### 3.4.3 密钥安全

Android 用 Keystore、iOS 用 Keychain，都必须走原生插件，不能落明文。
底线三条：Key 唯一明文出现位置是请求头；日志与错误上报里屏蔽；备份文件默认不含 Key。
H5 调试态允许只存内存，但要在页面上明示"刷新即失效"。

#### 3.4.4 公式渲染是红利，但要防长文

WebView + KaTeX 在双端都成立，比原生自绘省事得多。风险转到长文：
一份解答可能有 60 个以上公式，逐条挂 WebView 会卡。
方案：**一屏一个渲染宿主 + 结果按公式文本缓存**，同屏超过 40 个公式时改为分段懒渲染。

#### 3.4.5 导出与打印

复习资料的 PDF 自绘不迁。改为 HTML 排版后调系统打印/分享。
验收标准从"PDF 里公式位置准确"改为"打印预览里公式不溢出、分页不切断步骤"。

#### 3.4.6 后台任务

取消 WorkManager 后，日汇总、周报、掌握度重算改为：进首页时按"上次计算时间"增量补算。
代价是"打开就能看到昨天的数据"变成"打开后一秒内补齐"，要在首屏给骨架屏而不是空态。

#### 3.4.7 流式传输：uni.request 在 App 端拿不到 chunked

T5 查文档时确认的一件事：`uni.request` 的 `enableChunked` / `onChunkReceived` 标注为
**微信小程序**能力，Android / iOS 的 App 端与 H5 都不走这条通道。原计划"直接开流式"行不通。

三条路：

| 方案 | 代价 | 结论 |
| --- | --- | --- |
| H5 用 fetch + ReadableStream，App 用原生插件（plus.net 增量或 UTS 插件） | 双端各写一套传输 | 推荐 |
| 全平台退化为非流式（一次性返回） | 首字延迟 10-30 秒，学生只看到转圈 | 保底方案，必须能一键切 |
| 自建中转服务 | 违反 BYOK 直连，也违反"无后端" | 否决 |

工程上的应对：编排层不认传输。`runSolve` 只依赖 `LlmTransport` 接口（异步产出 chunk），
换驱动不动解析、重试与四阶段顺序。界面按"有 delta 就增量渲染，没有就等一次性结果"写，
两种传输同一套 UI。

**T5b 的落地状态**：

- `stream`（fetch）：已实现，并在 Node 里用本地 HTTP 服务验证过粘包、401、404、中途取消、
  连不上五种情况，还跑通了一次"真 HTTP + 真四阶段"的端到端。H5 直接可用。
- `buffered`（uni.request，非流式）：已实现，双端都能跑，**App 当前的默认值**。
- App 的流式通道**未验证**：能不能用取决于 webview 的跨域策略与外网访问。
  T13 真机验过再改默认值，调用方不用动——选型收在 `createTransport` 一处。

### 3.5 旧数据迁移

**实施时更正了一处（T3 实测）**：原计划让 0.8.0 新增"导出全部数据"产出一个新 JSON，
实际上 0.8.0 的备份包（zip）里本来就有 `db/totop.db`——一份完整的 SQLite 快照。
再养一套导出格式等于多一次出错机会，所以 1.0 直接读这份库。**0.8.0 侧不需要任何改动。**

| 步骤 | 做法 | 验收 |
| --- | --- | --- |
| 1 | 学生从旧版导出备份 zip（0.8.0 已有此能力） | 备份包里有 `manifest.json` 与 `db/totop.db` |
| 2 | 1.0 解包，把 `db/totop.db` 落到应用私有目录，以第二个连接打开 | 能读到 `mistake_record` 表，否则判定选错文件 |
| 3 | 按表拷贝，**列取新旧交集**：旧版本缺的列由新表默认值补上 | v1 到 v10 的备份都能进来，不必逐版本写迁移 |
| 4 | 图片随 zip 解到应用私有目录，题目行里的路径重新指向新位置 | 导入后错题缩略图不空白 |
| 5 | 整个导入放在一个事务里，失败整体回滚 | 中途失败后本地仍是干净空库 |

三条实现约定：

- 设置项按**白名单式过滤**拷贝：键名命中 `key` / `token` / `secret` / `password` 的一律跳过。
  Key 本该只在系统钥匙串，但旧版本可能漏在设置表里，导入时不能把它带过来。
- 成绩的 `importedAt` 取**考试场次的 `createdAt`**，不是考试日期。补录上周月考时，
  考试日期比录入时间还早，用日期排序会让"最近一次导入"挑错记录。
- 旧资料库的方法卡迁成 `material` 里 `source='legacy_card'` 的条目，标题为空时用方法名兜底。
  学生攒过的东西不能因为产品口径改了而消失。

迁移代码只写一次，双端共用。**不允许直接打开旧 App 的私有库**（双端都没有这个能力，
也不该有）；能读的只有学生自己选中的那个备份文件。

### 3.6 双轨期的纪律

- `legacy/android/` 只接受两类提交：致命崩溃修复、数据导出能力。其余一律拒绝。
- 新功能只进 `apps/mobile/`，不许为了"两边一致"回头改原生版。
- 双轨期结束的标志：1.0 正式版发布且连续两周无回滚。届时原生工程归档，仓库 README 改为单一入口。

### 3.7 迁移风险表

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 无离线 OCR 导致识别质量下降 | 高 | 手写题准确率下滑 | 上传分辨率抬高到 1600（L1），并在识题阶段要求模型回显不确定处 |
| iOS 审核因"自带 Key 直连模型"被问询 | 中 | 上架延迟 | 设置页明确写"用户自备密钥，本应用不提供任何模型服务" |
| 长文公式渲染卡顿 | 中 | 解答页体验 | 分段懒渲染 + 缓存，见 3.4.4 |
| 双端样式不一致 | 高 | 观感割裂 | design token 只在一处定义，禁止页面写死 px/色值 |
| 迁移期需求继续变 | 高 | 工期失控 | 1.0 需求冻结，新想法进 1.1 清单 |

## 四、底座二：移除旧安卓性能限制

### 4.1 放开清单

| 项 | 0.8.0 | 1.0 | 保留的兜底 |
| --- | --- | --- | --- |
| 动效 | 只位移+淡入 | 允许共享元素转场、叠化、一次性进度动画 | 页面切换总时长 ≤ 320ms；禁止常驻循环动画（思考指示除外） |
| 列表 | 分页 200 条 | 50 条一页，滚到底自动续 | 缩略图懒加载保留 |
| 图表 | 降采样 60 点、无动画 | 120 点、允许 240ms 入场动画 | 数据点超过 120 自动聚合 |
| 图谱 | 单屏 80 节点、静态 | 150 节点、可缩放平移 | 预计算坐标保留 |
| 图片 | 长边 1280 | 1600，质量 0.85 | 低于 3GB 可用内存或移动网络时降到 1280 |
| 取色 | 禁动态取色 | 仍禁用 | 理由改为品牌一致性 |
| 骨架屏 | 仅列表 | 全页统一骨架 | 数据到位后 120ms 内完成替换，避免闪烁 |
| 启动 | 固定 620ms 动画 | 跟随真实就绪，最快 320ms | 就绪判定超过 2 秒时显示进度说明 |

### 4.2 三档性能策略

不再用"一刀切禁用"，改为运行时分档：

| 档位 | 触发 | 表现 |
| --- | --- | --- |
| 高档 | 内存 ≥ 6GB 且系统动画未关闭 | 全部动效、1600 图、120 点图表 |
| 中档 | 默认 | 动效保留但时长 ×0.8，1280 图 |
| 省电 | 低电量模式或系统关闭动画 | 只保留淡入，图表无动画，公式分段渲染 |

档位只影响"表现"，不影响"功能"。**任何档位下都不许出现"这个功能在你这台机器上没有"**。

### 4.3 四条不能跟着放开的东西

| 项 | 为什么不动 |
| --- | --- |
| 图片压缩 | 不压缩意味着单题 5-8MB 上传，学生的流量与等待时间都是真金白银 |
| 公式渲染宿主数量 | 这不是老机限制，是 WebView 的固有限制，双端都一样 |
| 图谱预计算坐标 | 运行时力导向在弱网/低端机上会算出不同的图，同一份数据两次打开长得不一样 |
| 错误提示的粒度 | 与性能无关，但容易被"优化"掉：错误必须分到"Key 无效/余额不足/网络不通/模型名错"，不许笼统 |

#### 5.3.9 单选 / 多选不确定时的策略

现状是 `ChoiceAnswerGuard` 按题干字样猜单选多选，猜错就拦掉多字母答案。1.0 改为三级：

| 级别 | 判据 | 处理 |
| --- | --- | --- |
| 强证据 | 题干明写"多选/不定项"，或选项区标注多选 | 按多选处理，答案可含多个字母 |
| 弱证据 | 题型判为单选，但模型给了两个以上字母 | **不拦截**：按多选呈现，答案上方加一行确认条"这题可能是多选，已按多选给全"，可一键改回单选 |
| 无证据 | 字母数与题型一致 | 直接呈现，不打扰 |

三条底线：

1. **永不静默丢字母**。宁可多给一个字母让学生自己判断，也不能把答案截断成一个。
2. **确认条只出现一次**，不重复追问；学生改过一次后记住这道题的判定。
3. 确认结果写回题目，下次打开不再问。

| 编号 | 改动点 | 优先级 | 依赖 |
| --- | --- | --- | --- |
| S-47 | 实现上述三级策略，替换现有拦截式判定 | P1 | D-M4 |
| S-48 | 确认条文案不超过 20 字，两个动作："是单选" / "对，多选" | P1 | 无 |
| S-49 | 判定结果持久化到题目记录 | P2 | D-M2 |

前三档已实现（T6）：`judgeChoice` 只给结论、不改答案。单选却多字母时出一条确认条让学生选，
多选只给一个字母时提示核对，答案里认不出字母（例如写了 E）时如实说明。
**永远不截断字母**——0.8.0 把 "A、C" 截成 "C"，是本项目最不能重演的错。
S-49 的持久化等错题仓储（T9），现在确认结果只在本次运行内有效。

#### 5.3.10 对话里纠正之后：改写整段过程，不是改答案

这是"改错"的第三个入口。**三个入口共用同一个改写内核**：

| 入口 | 触发 | 写什么 |
| --- | --- | --- |
| 抽屉"导入标准答案" | 学生导入老师或教辅的答案 | 完整过程 |
| 解答卡"改错" | 学生自己发起 | 完整过程 |
| 对话订正 | AI 在追问里推翻了自己先前的结论 | 完整过程 |

**0.8.0 的问题是只写了一半**：`applyCorrection` 只替换 `finalAnswer` 与标准解答里的
`finalAnswer` 字段，步骤、依据、易错点都没动。后果是解答卡会出现自相矛盾的画面——
答案是 C，往下读步骤，推的却是 A、C。学生复习时看到的正是这套错位的东西。

| 编号 | 改动点 | 优先级 | 依赖 |
| --- | --- | --- | --- |
| S-51 | 改写范围扩到**整段过程**：步骤列表（每步内容 + 依据）、最终答案、易错点一起替换 | P0 | D-M4 |
| S-52 | 回写前做**自洽校验**：步骤推出的结论必须等于最终答案。不一致就不写，并提示"这次只给了结论，没给过程，让它重讲一遍" | P0 | D-M4 |
| S-53 | 模型写了订正标记却没给新步骤时，视为"未完成订正"：不采信、不改库、只在气泡上说明，不许用旧步骤配新答案 | P0 | D-M4 |
| S-54 | 旧过程留为"上一版"，可回退；回退后错题本与解答卡一起回到旧版，不许只回一半 | P1 | D-M2 |
| S-55 | 回执改成"已改写这道题的解答过程"，并让解答卡当场刷新为新版 | P1 | D-M4 |
| S-56 | **不动**学生步骤、错因、知识点归属、复发计数：这是同一道题的结论修正，不是重新做错一次，动了会让掌握度凭空多算一轮 | P0 | D-M2 |
| S-57 | 补小问仍走"追加"而不是覆盖：订正改的是同一问的结论，补的是之前没入库的另外几问 | P1 | D-M2 |
| S-58 | 题未入库（没有错题记录）时给可执行回执，不许假装已写入 | P1 | D-M2 |

**验收标准**

1. 让 AI 在追问里改错一道选择题的答案，错题本里的**步骤**也跟着变，不只是答案。
2. 解答卡上不存在"答案是 C、步骤推 A、C"这种错位；随便抽 10 道被订正过的题，逐条对上。
3. 模型只回一句"答案是 C"而没给过程时，库里不变，气泡上有一句说明。
4. 回退一次，错题本与解答卡同步回到旧版，刷新后仍一致。
5. 订正前后，这道题的知识点归属、复发次数、掌握度不变（掌握度只因"做对了/仍不懂"变）。

（红 <40 / 黄 40-70 / 绿 >70，与详情页分数的颜色同源）。详情页是看掌握度的唯一入口：
数值 + 最近 5 次变化 + 该知识点的错题列表，没有趋势图——两个点画出来的线会让人
误以为在稳定上升。

掌握度算法的四条约定：

| 事件 | 变化 | 说明 |
| --- | --- | --- |
| 做对 | `+ (1 - score) × 0.30` | 越接近 1 增益越小，避免一道题跳到 0.95 |
| 仍不懂 | `- score × 0.35` | 学生自己承认没懂，权重最高 |
| 新错题 | `- score × 0.20` | 可能只是算错，权重低于"仍不懂" |
| 初始 | `0.5` | 没有数据时既不奖励也不惩罚 |

**不做时间衰减**：表现是"我什么都没做，分数怎么掉了"，解释成本远大于收益。
"做对"的生产者现在只有错题详情的"这题我会了"（5.8 巩固练习落地后会成为主要来源）；
没有它的话，掌握度只会因为错题一路下跌。

| ST-5 | 删除与卡点笔记、复习打卡相关的设置项 | P0 | 无 |

**验收标准**

1. 设置项与页面能力一一对应，没有指向已下线功能的开关。
2. 性能档位切换后立即生效，不需要重启。
3. Key 在任何日志、导出文件、错误提示中都不出现明文。

**落地情况（T12）**：模型三联（地址 / 模型名 / Key）从拍题页搬到这里，与拍题页共用同一个
store，改完回去立即生效；性能档位（自动 / 高档 / 省电）存在 settings 表、下一张图就按新档位处理；
科目多选立刻落库；用量说明写清"1.0 起每次拍题都调视觉模型"；
关于区显示应用、领域层、提示词与库结构版本；备份导入按钮是禁用态（解 zip 与图片落盘在 T13）。

**Key 仍只在内存**：系统钥匙串必须走原生插件（Kotlin/UTS），当前仓库没有这个能力，
所以宁可让它每次重填，也不写进 settings 表或 uni storage——那等于把学生 Key 明文留在沙箱里。

### 7.1 批次划分

| 批次 | 目标 | 内容 | 出口条件 |

| B4 | 主界面成型 | M5 + 5.3 的删除项与抽屉 | 首页无标语无拍题卡；拍题页无验算/复述/存资料库/我已理解 |

| B6 | 收尾 | M8 + 陪伴页 + 设置 + 双端真机验收 | 双端全流程走通，截图归档 |

### 7.2 顺序上必须遵守的三条

1. **先删后加**。5.3.8 的删除项（复述、存资料库、验算、我已理解）必须在 B4 之前完成，
   否则 B5 的资料库与练习会建在旧结构上，等于白做。
2. **提示词改造放在正确的一步**。S-28 到 S-31（题型字段与骨架）必须在 B3 完成，
   不能等到 B5 边做练习边改——巩固练习共用同一套解析骨架。
3. **数据迁移早于内容迁移**。B1 不做完就开始搬页面，会反复改取数逻辑。

### 7.3 每批的固定产出

每批结束必须有三样东西，缺一样算没做完：

- 可安装包（双端或至少 Android）。
- 该批的验收记录（真机型号、通过项、未通过项）。
- `CHANGELOG.md` 与 `docs/偏离记录.md` 的对应条目。

## 九、验收标准

### 9.1 全局门禁

| 项 | 标准 |
| --- | --- |
| 双端一致 | 同一页面在 Android 与 iOS 上文案一致、交互一致，差异只允许出现在系统级控件 |
| 无死入口 | 每个可点元素都指向存在的页面或动作 |
| 无孤儿页面 | 每个页面都有入口；下线页面的文件已删除，不是隐藏 |
| 公式 | 十科样例题中，公式、上下标、分式、化学方程式均无溢出、无乱码、无 `\frac` 原文泄漏 |
| 错误提示 | 失败必须分到具体原因（Key 无效 / 余额不足 / 网络不通 / 模型名错 / Base URL 错），禁止"请求失败" |
| 数据 | 旧数据导入后条目数与 0.8.0 一致，抽查 5 道错题内容一致 |
| 解答自洽 | 每份解答的步骤必须能推出它的最终答案；被订正过的题，错题本与解答卡同时是过程版，不存在"答案新、步骤旧" |
| 改写一致 | 三个改写入口（导入标准答案、改错、对话订正）落库结果结构相同，抽查任意两条记录字段一一对应 |
| 隐私 | Key 不出现在任何日志、导出、错误信息里；题目图片只发往用户配置的端点 |
| 性能 | 中档机 200 条列表滚动 ≥ 50 FPS；解答页首次可读 ≤ 2 秒（不含模型耗时） |

### 9.2 真机矩阵

| 端 | 机型要求 | 必测 |
| --- | --- | --- |
| Android | 一台 4GB 内存旧机 + 一台当前主流机 | 相机、裁剪、长列表、公式、打印 |
| iOS | 一台非刘海机型 + 一台刘海机型 | 安全区、相机权限、Keychain、打印 |

模拟器结论一律无效，沿用 `docs/低端机测试清单.md` 的判定原则。

第五章每节的"验收标准"即该页的验收条目，本章不重复。
每页验收通过后，在实施记录里打勾并附一张截图，作为 1.0 发布的证据。

## 十、1.0 明确不做

| 不做 | 理由 |
| --- | --- |
| 小程序端 | 需要备案域名与请求白名单，与 BYOK 直连冲突 |
| 端上离线 OCR | 双端各写一次桥接，收益低于成本（要做就进 1.1） |
| 账号与云同步 | 无后端是产品底线，不是技术债 |
| 判卷与正确率统计 | 从第一天起就不做，1.0 不改口径 |
| 复习打卡与间隔重复 | 巩固练习已经覆盖"今天该练什么"，两套机制并存只会互相打架 |
| 卡点笔记 | 下线。已写内容保留在库里，不删数据 |
| 掌握度雷达 / 趋势 / 错因分布 | 三个图表都没能回答"我下一步做什么"，删掉换成章节热力 |
| 错题状态分类（不会 / 存疑 / 错误 / 理解） | 分类没改变任何动作，学生不会因为"这条是不会"就换一种复习法；掌握程度统一去知识点页看 |
| 导出复习 PDF | 导出这件事收进复习资料一处，不再有两套导出 |

## 十一、口径确认记录

五处原本含糊的地方已逐条确认，下面是最终口径。**实施以本表为准，不要再按"更合理"的想法改回去。**

| 编号 | 结论 | 落在哪 |
| --- | --- | --- |
| Q-1 | 易错题**不要任何状态**：不会 / 存疑 / 错误 / 理解这套分类整块删掉，页面只留四个筛选。有没有掌握，去知识点页看 | 5.6（M-1 至 M-9） |
| Q-2 | "删除导出复习"就是删除易错题页顶部的"复习"按钮。复习资料里的 PDF / 打印导出**保留** | 5.6 M-3、5.10 R-5 |
| Q-3 | 学情选单科后，成绩区只显示该科目的导入内容，不串科 | 5.11（T-2、T-3） |
| Q-4 | "改错"**不是**标记状态，而是**把这道题里的解答过程整段换掉**：来源可以是导入的标准答案，也可以是对话里 AI 纠正自己后给出的新过程 | 5.3.5（S-22 至 S-27b）、5.3.8 S-44、5.3.10（S-51 至 S-58） |
| Q-5 | 底部 tab 本来就是四个（首页 / 拍题 / 陪伴 / 功能中心），1.0 不动 | 3.3、5.4 |

Q-1 与 Q-4 会连带两处，实施时别漏：

1. 拍题页的"这题我不会"写的是状态，状态删了它就没有效果，一并删除（S-50）。
2. 状态列保留只为导入旧数据，界面不再读；新录入不写状态（M-8、M-9、3.4.2）。
3. "改错"有三个入口（导入标准答案、改错按钮、对话订正），三处必须落到同一个改写内核；
   只改答案不改过程，算没做完（S-51 至 S-56）。
