# 真机验收清单（T13）

这份清单是 1.0 alpha 的**gate**：任何一条不过，就不算出包。逐条写清"怎么判"，
是因为"看起来能用"和"能用"之间的差距，正好是本项目所有设备侧代码的风险所在——
它们一行都没在真机上跑过。

## 一、前置

| 项 | 要求 |
| --- | --- |
| 机型 | 至少两台：一台高档（≥8GB，Android 12+）、一台中档（4GB 左右，Android 10） |
| 系统 | Android 优先；iOS 单独一轮（`plus.io` 与文件权限表现不同） |
| 网络 | 一个正常 Wi-Fi，一个限速到 200kbps 的弱网 |
| 模型 | 一个可用的 OpenAI 兼容端点 + Key（余额 ≥ 1 元，够跑 30 次） |
| 构建 | `pnpm --filter @totop/mobile run build:app` 后由 HBuilderX 云打包或本地打包 |
| 数据 | 一份 0.8.0 导出的备份 zip（没有就先用空库跑前 8 组） |

**记录方式**：每组记「通过 / 不通过 + 现象 + 截图」，不通过的直接开 issue，附机型与版本。

## 二、启动与首屏

| 编号 | 操作 | 通过标准 | 不通过先查 |
| --- | --- | --- | --- |
| S-1 | 冷启动（杀进程后点图标） | 高档机 ≤ 1.2 秒可点，中档 ≤ 1.8 秒 | 首屏是否等 `getDatabase()`；建表是否被挪到首帧后 |
| S-2 | 首次启动看首页 | 有骨架屏，1 秒内换成真内容；不出现白屏 | 数据库打开失败会在首页 error 文案里显示原因 |
| S-3 | 第二次冷启动 | 明显快于首次（不重复建表） | `SCHEMA_STATEMENTS` 是否都是 IF NOT EXISTS |
| S-4 | 首页不熟知识点为空时 | 整块不占位，没有空标题 | `hasWeak` 计算 |
| S-5 | 首页切到其他 tab 再回来 | 数字刷新，不闪白 | `onShow` 是否触发 `load()` |

## 三、拍题与图片管线（风险最高）

| 编号 | 操作 | 通过标准 | 不通过先查 |
| --- | --- | --- | --- |
| P-1 | 首次点"拍照" | 弹系统相机权限；拒绝后给可操作的提示，不是静默失败 | `uni.chooseImage` 的 fail 分支是否吞掉了 errMsg |
| P-2 | 拍一张清晰试卷 | 缩略图出现，无旋转 90 度问题 | `getImageInfo` 的 orientation 未处理——这是一类已知问题 |
| P-3 | 连拍 3 页 | 三张都进列表；同一页拍两次被去重 | sha256 去重逻辑 |
| P-4 | 删一张 | 列表移除，发送时确实不带它 | `removeImage` 下标 |
| P-5 | 大图（4000px 原图） | 上传的图长边 ≤1600（在设置里切"高档"再验一次） | `uni.compressImage` 的 px 参数是否被忽略 |
| P-6 | 切到"省电"档再拍 | 长边 ≤1280 | 性能档位是否真的传到 `resolveProfile` |
| P-7 | 相机被其他应用占用时 | 给出"相机打不开"的提示，能改用相册 | fail 分支 |
| P-8 | 相册选一张 20MB 的图 | 不 OOM、不卡死 30 秒以上 | base64 转换的内存峰值 |

## 四、解答链路

| 编号 | 操作 | 通过标准 | 不通过先查 |
| --- | --- | --- | --- |
| A-1 | 贴文字题干发送 | 有阶段提示（识题中/求解中/找错因），不是只转圈 | 非流式无 delta，阶段文案是唯一反馈 |
| A-2 | 拍照发送 | 同 A-1，且图片确实进了请求 | 请求体里 `image_url` 是否是 data URL |
| A-3 | 计时 | 非流式单题 15 到 40 秒内出结果 | 超过 120 秒会按超时收尾 |
| A-4 | 填错 Key（尾号改一位） | 提示"API Key 无效或没有权限，去设置里换一个" | `classifyHttpFailure` 的 401 分支 |
| A-5 | 填错模型名 | 提示"模型名不对" | 404 + 响应含 model |
| A-6 | 断网发送 | 提示"连不上模型服务"，不是白屏 | fetch/uni.request 的失败分支 |
| A-7 | 弱网（200kbps）发送 | 120 秒内要么出结果要么超时提示；不无限转圈 | 超时定时器 |
| A-8 | 发送后立刻点"停止" | 立刻停，不再计费；再次发送正常 | AbortController 是否传到 fetch/uni |
| A-9 | 答案解析出多个字母（单选题） | 出现确认条，答案不被截断 | `judgeChoice` |
| A-10 | H5 调试同一个 Key | 能流式（H5 自动走 stream） | `defaultTransportMode` |

## 五、落库与易错题

| 编号 | 操作 | 通过标准 | 不通过先查 |
| --- | --- | --- | --- |
| D-1 | 解答完成后 | 出现"已存进错题本"，点进去能看到这条 | `persist()` 的 catch 文案 |
| D-2 | 杀掉进程重开，进易错题 | 刚才那条还在 | 写库是否走了事务 |
| D-3 | 四个筛选逐个点 | 每次都能筛出正确子集；"清空筛选"复原 | 列表 SQL 的 where 拼接 |
| D-4 | 列表滚 200 条 | 中档机 50 FPS 以上，不掉帧 | 现在是 200 条一次性渲染，掉帧就要改虚拟列表 |
| D-5 | 详情页 | 能看到题目/答案/错因/步骤；**看不到任何"掌握程度"** | 状态字段是否被误读 |
| D-6 | 库里历史四种状态的数据（导入后） | 全部可见，条数与导入前一致 | `status` 是否参与了 where |

## 八、已知未验证项（出包时必须写进 README）

1. App 端 fetch 流式是否可用（当前 App 走非流式，H5 走流式）。
2. `uni.compressImage` 的 `width`/`height` 字符串参数在真机上的实际效果。
3. `plus.io.resolveLocalFileSystemURL` 读图片转 base64 的稳定性（大图内存峰值）。
4. 首页冷启动 1.2 秒 / 1.8 秒是否达标。
5. 易错题 200 条滚动的帧率。
6. iOS 端的文件路径与权限差异。
